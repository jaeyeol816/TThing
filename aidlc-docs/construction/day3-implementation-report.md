## 2. 검색이 아니라 지목이다

이 유닛의 설계를 한 줄로 줄이면 이것이다 (BR-S-01).

```
open_paths (세션이 좁혀 놓은 후보)
  -> EXAONE 이 질문과 관련된 것 선택        <- 본문 없이, 경로와 제목만
  -> 그 파일만 읽기
```

**없는 것**: 전역 파일 검색 · 벡터 유사도 · `corpus/**` 스캔.
`test_no_global_scan_in_source` 가 `rglob`·`glob(` 의 부재를 확인한다.

세션에 없는 것은 못 찾는다. 한계이자 **"지금 이 사람의 관심사"라는 강력한
사전 필터**다.

### 2.1 후보에 실행 로그를 넣지 않으면 시나리오 2 가 깨진다

`train.log` 는 `open_paths` 에 없고 `recent_runs[].log` 에만 있다.
`candidate_paths()` 가 `open_paths` + `recent_edits` + `recent_runs[].log` 를
합치는 이유다. 빠뜨리면 "지금 학습 중" 답이 불가능해진다.

### 2.2 경로 선택 프롬프트에 본문을 넣지 않는다 (BR-S-02)

이유가 두 개인데 두 번째가 본질이다.

1. 지연·토큰 비용
2. **경로 선택은 등급 판정 *전*에 일어난다.** 아직 어떤 파일이 기밀인지 모르는
   시점에 본문을 EXAONE 에 보내는 것은 순서가 뒤바뀐 것이다. 이번 구현의
   EXAONE 은 사외 SaaS 이므로 더욱 그렇다.

**실측**: 프롬프트 326자. 본문을 넣으면 수천 자가 된다.

```
[select_paths] 0.44s
  후보: corpus/customer-H/req-spec-2026H.md, corpus/kim/docs/auth-design.md,
        corpus/kim/notes/2025-11-auth.md
  프롬프트 길이: 326
  REQ-4412 부재 · EAP-AKA 부재 · CTR-204817 부재 · 12억 부재 · 보안등급 부재
```

출력은 **인덱스 배열**이다. 경로 문자열을 생성하게 하면 존재하지 않는 경로를
만들어내고, 그 문자열이 `read()` 의 경로 검사로 들어간다.

실패·형식 오류·선택 0개 → **후보 전체**를 반환한다. 더 많이 읽고 게이트키퍼가
막는 것이, 덜 읽고 답을 못 하는 것보다 낫다 (fail closed 방향).

### 2.3 읽기는 2중 검사다 (BR-S-03)

```
① safe_resolve()      MESH_DATA_ROOT 하위인가        -> 아니면 건너뛴다
② knowledge_scope glob 그 에이전트의 범위인가         -> 아니면 예외를 올린다
```

왜 처리가 다른가: 경로 탈출은 **세션 JSON 이 오래된 것**일 수 있으므로 그 파일만
건너뛴다. scope 위반은 **설정 오류이거나 공격**이므로 조용히 넘기지 않는다.

`Chunk.tier` 를 채우지 않는다. 등급 판정을 여기서도 하면 판정 로직이 두 곳에
생기고 한쪽이 느슨해진다. 예외가 하나 있다 — 승인된 QA(`verified_chunks`)는
**이미 판정된 등급을 옮겨온다** (BR-S-05). 새로 판정하는 것이 아니고,
Gatekeeper 가 `max()` 로 합치므로 재판정이 더 높으면 그쪽이 이긴다.

### 2.4 문서 종류가 시나리오 3 을 성립시킨다 (BR-S-09)

```
*/notes/*   -> note,       informal      <- 김책임 근거 (개인 메모, 2025-11)
*/docs/*    -> design_doc, official      <- 최민수 근거 (설계 리뷰, 2025-12)
*/runs/*    -> run_log,    official      <- 마지막 200줄만 읽는다
```

화면에 이 차이를 표시하는 것이 **"둘 다 사실일 수 있습니다"라는 서술을
뒷받침한다.** 시점과 공식성이 없으면 그 문장은 근거 없는 위로가 된다.

## 3. 지목 목록은 인증 없이 보인다

`list_agents()` 가 만드는 `current_focus_summary` 는 `Session.focus` 원문이
아니다. 여기서 고객사명이 새면 **게이트키퍼를 우회한 유출**이다 (FR-31).

설계는 "게이트키퍼로 식별자 제거 요약"이었다. 구현하면서 방식을 바꿨다 (§4.2).

```python
FOCUS_TOPICS = ("인증 관련 작업", "데이터 파이프라인 작업", "모델 학습 작업",
                "배포·릴리스 작업", "문서 검토", "성능 분석", "기타 작업")
```

모델이 **닫힌 라벨 집합에서 하나를 고른다.** 등급 판정과 같은 방식이다.
범위 밖이면 `None` — 표시하지 않는다. **원문 폴백은 없다.**

**실측** (각 0.23~0.26s):

| 세션 `focus` (원문) | 라벨 |
|---|---|
| 고객사 H 인증 요구사항 검토 + SDK v3.2 토큰 정책 | 인증 관련 작업 중 |
| atlas-ml 전처리 v3 재학습 | 모델 학습 작업 중 |
| SDK v3.2 배포 준비 | 배포·릴리스 작업 중 |

캐시 키가 `(entity_id, updated_at)` 이라 세션이 갱신되면 자동 무효화된다.
앱 시작 시 워밍업해 첫 화면에서 기다리지 않게 한다.

`disclose` 를 존중한다. 꺼진 필드는 `None` 이고 UI 는 "비공개"라고 쓰지 않고
**아예 렌더하지 않는다** — "비공개"라는 표시 자체가 정보다.
`expertise` 는 끌 수 없다 (`Literal[True]`) — 끄면 지목이 불가능해진다.

## 4. 설계 결함 2건 (Day 3 에 발견)

상세는 `preflight-findings.md` §11.

### 4.1 초안 입력이 전부 경계를 넘어서는 안 되는 것들이었다 🔴

`BR-AG-04` 는 초안 프롬프트에 "변환된 페이로드 · 부분 응답 · 세션 사실 ·
인용 목록(`display_title` 만)"을 넣으라고 했다. 하나씩 확인해 보니
**뒤 세 개가 전부 나가서는 안 되는 것**이었다.

| 넣으려던 것 | 왜 안 되는가 |
|---|---|
| 근거 제목 | `"고객사 요구사항명세서"` 에 고객사가 있다 (FR-43 과 같은 이유) |
| 근거 시점 | 일정·날짜는 `_intentionally_absent` 목록에 있다 |
| 세션 사실 | `Session.focus`/`summary` 는 원문 취급이다 |
| 부분 응답 | 어휘 사전 밖 자유 문자열이라 검증 2단계를 통과할 수 없다 |

설계가 "`display_title` 만"이라고 쓴 것은 `internal_path` 와 비교한 말이었지만,
**경계를 넘는 맥락에서는 제목도 원문 파생물**이다.

**조치** — 두 단계로 나눴다.

```
① 경계 밖:      이미 검증을 통과한 envelope 을 그대로 재사용
                (프롬프트와 모델만 바뀐다 -> haiku)
                모델은 구조 페이로드만 보고 summary / draft_answer 를 쓴다

② 신뢰 구역 안:  제목 · 시점 · 공식성 · 세션 사실을 situation 에 덧붙인다
```

`Gatekeeper.ask_draft()` 가 ①을 담당한다. 새 페이로드를 만들지 않으므로
검증을 다시 통과시킬 필요도, 검증 없이 나가는 경로도 없다.

초안 품질은 유지된다 — 담당자가 먼저 읽는 것은 "무엇을 근거로 하는가"이고
그건 애초에 모델이 만들 수 없는(=만들면 안 되는) 정보다.
그래서 `situation` 의 순서도 로컬 사실이 먼저다.

### 4.2 목록 요약을 자유 문장으로 만들면 검사할 방법이 없다 🔴

자유 문장 요약은 **그 문장에 원문이 섞였는지 사후에 검사해야 한다.**
이건 §3.1 에서 기각한 구조다 — "무엇을 지울까"이고 검사를 잊으면 유출이다.
그리고 이 화면은 인증 없이 보인다.

**조치** — 닫힌 라벨 집합(§3). 원문이 섞일 채널이 **존재하지 않는다.**
검사할 것이 없으므로 잊을 검사도 없다.

### 4.3 배선 결함 2건

**브로커를 누가 만드는가.** `main.py` 가 `BrokerClient` 를 만들면 경계를 넘는
모듈이 하나 늘어난다 (SECURITY-11). 허용 목록이 늘어나면 "단일 통로"가
무의미해진다. → `Gatekeeper.build()` 팩토리로 **생성도 통로 안에** 뒀다.
`main.py` 는 브로커의 존재를 모른다.

**`api_models` 의 레이어.** Day 1 에 U3 소유라는 이유로 L5 에 뒀는데,
`inbox.py`(L5)가 쓰려면 같은 레이어를 import 해야 한다. **레이어는 소유가
아니라 의존 순서다** → L1 로 내렸다.

## 5. Orchestrator — 모델을 부르지 않는다

```python
def branch(answers, *, auto, escalate) -> Disposition:
    if any(not a.citations for a in answers):
        return Disposition.ESCALATE          # ⚠️ 신뢰도보다 먼저
    conf = min(a.confidence for a in answers)
    ...
```

**인용 검사가 신뢰도보다 먼저인 것이 이 함수의 전부다** (BR-O-04).
이 순서가 자동 응답의 인용 준수율을 **구조적으로** 100% 로 만든다.
신뢰도를 먼저 보면 "0.99 인데 근거가 없는 답"이 사용자에게 도달한다.

2명일 때 `min()` 을 쓰는 이유: 약한 답이 강한 답에 편승하지 않게 (BR-O-05).

### 5.1 답을 버리지 않는다

```python
divergent = text_differs and source_differs   # LLM 호출 없음
```

`conflict` 가 아니라 `divergent` 인 것이 설계 결정이다.
`conflict: true` 는 **단정**이고 `divergent: true` 는 **관찰**이다.
두 조건의 논리곱이고, 두 번째 조건(근거 문서가 다르다)이 오탐을 줄인다 —
같은 문서를 근거로 표현만 다르게 말한 것은 상충이 아니다.

`merge()` 는 요청 순서를 유지한다. 신뢰도로 정렬하면 사용자가 위쪽 답을
정답으로 읽고, 화면이 매번 달라지면 데모도 흔들린다 (BR-O-07).

> 하나를 조용히 고르면 나머지 하나는 영원히 묻힌다.

### 5.2 하위 질문별로 처분을 분리한다

전체를 묶어 `branch()` 하면 `min()` 때문에 **이미 답이 나온 조각까지**
에스컬레이션된다. 그래서 `_send_all()` 은 두 단계다.

```
① 모든 답을 모으고 call 단위로 처분을 정한다
② 그다음 에스컬레이션한다
```

②가 ① 뒤인 것이 `already_answered` 를 채우기 위해서다 — "다른 조각은 이미
답변됨"을 알려면 다른 call 의 처분을 먼저 알아야 한다. 이 필드가 시나리오 2 의
장치다. 담당자가 **자기가 답해야 하는 조각만** 본다.

### 5.3 모델 호출 코드가 없다

설계의 완료 기준은 `grep -c "exaone|bedrock|broker" == 0` 이었다. 문자열
검사는 `reason="broker_unavailable"` 같은 **이유 코드**까지 잡으므로 ast 로
바꿨다 — import 와 모델 메서드 호출(`complete_json`·`invoke`·`converse`)을
정확히 본다.

## 7. 인박스 — 전달이 아니라 가공이다

> 담당자에게 질문 원문만 던지면 **알림이 하나 늘 뿐이다.**

항목이 4개를 담는다: 요약 · 근거 · 그대로 승인 가능한 초안 ·
**Agent 가 이미 답한 조각**.

`UPDATE` 는 `status`/`resolved_at`/`resolution_text`/`redirect_to` **만**
건드린다. `draft_*`·`situation_json`·`citations_json` 은 감사 흔적이다 —
"무엇을 근거로 이 초안이 만들어졌나"를 나중에 확인할 수 있어야 한다.
`test_update_touches_only_mutable_columns` 가 SQL 의 대상 컬럼을 파싱해 검사한다.

**자동 재지목을 하지 않는다** (BR-I-03). `not_me` 는 질문자 화면에 표시하고
질문자가 다시 누른다. 현실에서 벌어지는 일과 같고, **사람이 지목했으므로
정확하다.** 자동 재지목을 넣으면 오라우팅이 연쇄된다.

승인 시 `VerifiedQA` 로 환류하며 **`tier` 를 보존한다** (BR-I-02).
`not_me` 는 환류하지 않는다 — 담당자가 답을 준 것이 아니다.

### 8.1 대역이 검증을 우회하지 않는다

```
ExaoneClient / BrokerClient      대역
조립 · 검증 · 감사 · 재수화        **실제 코드**
```

목업 모드의 원칙과 같다 (FR-48). 이걸 깨면 테스트가 통과하는데 실물이 새는
상태가 된다.

### 8.2 테스트가 아무것도 검사하지 않던 두 곳

1. `TestClient` 의 기본값이 `raise_server_exceptions=True` 라서 전역 예외
   핸들러가 만드는 500 응답을 볼 수 없었다. "응답에 스택 트레이스가 없다"를
   확인하려던 테스트가 **예외를 그대로 받고 있었다.**
2. "소스에 `StaticFiles` 가 없다" 같은 문자열 검사가 **주석까지 잡았다.**

같은 문제를 Day 2 에도 겪었다 (`store` 의 `classify` 검사가 `classify_source`
를 잡았다). **문자열 검사는 주석과 무관한 이름까지 잡는다.** 구조를 검사해야
할 때는 ast 를 쓴다.

### 8.3 "유출"의 의미를 다시 나눴다

시나리오 테스트에서 `김철수` 가 응답에 있다고 실패했다. `agent_label` 이
`"김철수 책임의 Agent"` 였다.

| 위치 | 고객사명·계약번호 | 지목한 사람 이름 |
|---|:---:|:---:|
| 페이로드 (경계를 넘는 것) | ✕ | ✕ |
| 감사 로그 (페이로드 사본) | ✕ | ✕ |
| API 응답 (신뢰 구역) | ✕ | **○** |

사용자가 **직접 지목한 사람**의 이름은 신뢰 구역에 머문다. 고객사명은 사용자가
알려준 것이 아니라 문서에서 온 것이므로 어디에도 나와서는 안 된다.
Day 2 에 배운 구분(`NEVER_ANYWHERE` vs `NEVER_IN_PAYLOAD`)을 여기서도 적용했다.
