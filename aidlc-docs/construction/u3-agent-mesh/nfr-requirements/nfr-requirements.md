## 1. 성능

| ID | 요구사항 | 목표 | 근거 |
|---|---|---|---|
| P-01 | `prepare` (1명) | < 6s | EXAONE 실측 **0.42s** × 3회 (`enable_thinking=False` 로 개선) |
| P-02 | `prepare` (2명) | < 7s | 병렬 |
| P-03 | `send` (1명) | **< 12s** | **Bedrock 실측 9.23s** (460 in / 513 out) |
| P-04 | `send` (2명) | **< 14s** | 병렬이므로 +2s |
| P-05 | 에스컬레이션 초안 | < 3s | haiku-4-5. 출력이 짧다 |
| P-06 | `GET /api/agents` (캐시 히트) | < 50ms | 목록은 화면 진입 시 필요 |
| P-07 | `GET /api/inbox` | < 50ms | SQLite 인덱스 |
| P-08 | `GET /api/audit?q=` | < 200ms | 레코드 수십 건 규모 |
| P-09 | **전체 상한** | **30s** | FR-36 |

**P-03 수정 이력**: 설계 시점의 2.17s 는 4 토큰 응답 기준이었다.
실제 답변(이유 + 완화안 3개)은 513 토큰이라 9.23s 다 — **출력 토큰이 지연을 지배한다.**
상세: `preflight-findings.md` §2 발견 4-b.

합계 약 18s 로 상한 30s 대비 여유 12s. 여유가 줄었으므로 **재시도를 남발할 수 없다** —
타임아웃을 재시도하지 않는 정책(BR-E-05)이 여기서도 옳다.

**병렬화 지점**: 2개 대상에 대한 `prepare`와 `send`를 `asyncio.gather`로 처리한다. 순차로 하면 12s → 예산의 40%를 먹는다.

**캐시 워밍업**: 앱 시작 시 `list_agents()`를 한 번 호출해 `current_focus_summary` 캐시를 채운다. 사용자가 첫 화면에서 3초를 기다리면 안 된다.

### 2.1 SECURITY-08 상세 — 인가가 없는 상태를 어떻게 다루는가

사용자 인증·인가는 요구사항 §7에서 **명시적으로 범위 밖**이다 (사용자는 드롭다운으로 전환).
그러므로 객체 수준 인가(IDOR 방지)·기능 수준 인가·토큰 검증은 **N/A**다.

**대신 다음 4개로 위험을 대체 완화한다.**

| # | 대체 통제 | 무엇을 막나 |
|---|---|---|
| 1 | `127.0.0.1` 바인딩 강제 | 외부에서 접근 자체가 불가 |
| 2 | 인용에서 `internal_path` 제거 (FR-43) | 권한 없는 문서의 경로·본문 노출 |
| 3 | `prepare`/`send` 2단계 승인 | 사용자 확인 없는 외부 전송 |
| 4 | `knowledge_scope` glob 검사 (U2) | 에이전트 간 지식 격리 |

**실배포 요건 (README에 명시)**: 이 시스템을 실제로 도입하려면 **원본 시스템의 접근 권한을 반드시 승계**해야 한다. 그러지 않으면 권한 우회 도구가 된다. 요구사항 §7과 설계 §10.1에 이미 기록돼 있고, 코드에도 `# TODO(prod): inherit source-system ACL` 주석을 남긴다.

### 2.2 레이트 리밋 (SECURITY-11)

localhost 전용이므로 네트워크 레벨 레이트 리밋은 불필요하다.
대신 **비용 폭주 방어**로 다음을 둔다.

| 제한 | 값 | 이유 |
|---|---|---|
| `AgentConfig.daily_limit` | 50 / 에이전트 | Bedrock 비용 |
| `MAX_TARGETS` | 2 | 설계 §4.4.4 |
| `envelope` 캐시 `take()` | 일회용 | 중복 전송·중복 과금 방지 |
| 진행 중 요청 | 5개 (세마포어) | 동시 사용자 1~5명 |

실제 레이트 리밋은 U5의 API Gateway Usage Plan이 담당한다 (5 rps / burst 100 / 일일 2000).

### 2.3 남용 시나리오 (U3 범위)

| # | 남용 | 방어 |
|---|---|---|
| 1 | 같은 `envelope_id`로 반복 전송해 비용 유발 | `take()`가 일회용 |
| 2 | 3명 이상 지목으로 비용 유발 | `MAX_TARGETS=2` (pydantic) |
| 3 | 4000자 질문 반복 | 길이 제한 + `daily_limit` |
| 4 | 인박스 `resolve`를 남의 항목에 호출 | **MVP 한계.** 인증이 없어 막을 수 없다. 실배포 요건으로 기록 |
| 5 | Agent 응답에 임의 `ref`를 넣어 재수화로 문자열 주입 | U1 BR-G-10 (매핑에 없는 ref는 치환하지 않음) |
| 6 | `/api/audit?q=`에 SQL 인젝션 | 파라미터화 쿼리 |

4번은 정직하게 한계로 남긴다. 로컬 단일 사용자 데모에서는 문제가 아니고, 실배포에서는 인증이 전제다.

## 3. 신뢰성

| ID | 요구사항 |
|---|---|
| R-01 | `asyncio.wait_for(30s)`. 타임아웃 시 도착한 답만 반환 + 나머지 에스컬레이션. 하나도 없으면 `answer_in_zone()` |
| R-02 | 2명 중 1명 실패 시 나머지 1명 답변을 반환한다 (`return_exceptions=True`) |
| R-03 | 브로커·Bedrock 오류 → `answer_in_zone()` + 사용자에게 품질 저하 고지 |
| R-04 | `envelope` 만료 → 410 Gone + "다시 질문해 주세요" (조용히 실패하지 않는다) |
| R-05 | Inbox 쓰기 실패 시 사용자에게 에스컬레이션 실패를 알린다. 조용히 삼키지 않는다 |
| R-06 | 필수 시스템 프롬프트 문구 누락 시 **예외를 던진다** (조용히 진행하지 않는다) |
| R-07 | 매핑 폐기는 `try/finally`. 재수화 실패 시에도 폐기 |

**R-02가 시나리오 3에 필요하다.** 2명 지목에서 한쪽이 실패해도 다른 쪽 답은 보여야 한다.

## 7. 관측 가능성

| 항목 | 구현 |
|---|---|
| 요청 추적 | `correlation_id` (`contextvars`) + 응답 헤더 `X-Correlation-Id` |
| 단계별 지연 | 각 단계 소요를 로그에 기록 (`prepare.classify`, `prepare.extract`, `send.agent`) |
| 처분 분포 | `AUTO`/`UNVERIFIED`/`ESCALATE`/`BLOCKED` 카운터 → 자동 응답률 측정 (성공 기준 ≥50%) |
| 인용 준수 | `AUTO` 중 인용 ≥1 비율 → 항상 100%여야 한다 |
| 방지된 인터럽트 | `AUTO` 건수 × 20분 추정 (FR-44) |
| `/api/health` | 모드·모델·경계 URL·미러 지연·`trust_boundary_simulated` |

**처분 분포와 인용 준수가 그대로 평가 지표다** (요구사항 §6). 별도 계측 코드를 만들지 않고 카운터를 `/api/health`에 노출해 U6 평가 하네스가 읽는다.
